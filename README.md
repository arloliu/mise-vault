# mise-vault

Private [mise](https://mise.jdx.dev) backend plugin
that distributes centrally approved developer tools inside the company network.

Tools are served from the private Nexus,
the approved-version catalog lives in this repository,
and developers use ordinary mise commands —
no Nexus URLs, archive layouts, checksums, or backend names to learn.

```bash
mise ls-remote go          # lists company-approved versions only
mise use go@1.26.0
mise install               # in any project with mise.toml or .tool-versions
```

Only versions listed in this repository's catalog are installable.
An artifact merely existing in Nexus is not enough;
the catalog is the company allowlist.

## Workstation setup (one time)

Prerequisites: `mise`, `git`, `curl`, and `~/.netrc` credentials for the GitLab and Nexus hosts
(see the internal onboarding page for credential setup).

```bash
git clone -q --depth 1 \
    https://gitlab.company.example/devtools/mise-vault.git /tmp/mise-vault-bootstrap
/tmp/mise-vault-bootstrap/install.sh
```

This installs the exact commit you cloned — the current approved catalog
(every commit on the default branch has passed merge review and CI).
To pin a specific release instead, add `-b <tag>` to the clone.
The installer is idempotent — re-running it is safe.
It configures user-scoped mise settings,
installs this plugin pinned to the exact version you cloned,
and generates `~/.config/mise/conf.d/mise-vault.toml`
(tool aliases; regenerated by tooling — never edit it by hand).

For CI or any environment that has a GitLab token instead of netrc:

```bash
curl -fsSL --header "PRIVATE-TOKEN: $GITLAB_TOKEN" \
    "https://gitlab.company.example/api/v4/projects/devtools%2Fmise-vault/repository/files/install.sh/raw?ref=<ref>" \
    | MISE_VAULT_REF=<ref> \
      MISE_VAULT_REPO_URL=https://gitlab.company.example/devtools/mise-vault.git bash
```

(The downloaded file has no git checkout to self-detect from, so both variables are required;
`MISE_VAULT_REF` accepts a tag, a commit, or `latest`.)

## Updating

```bash
mise run vault-sync latest    # newest approved catalog
mise run vault-sync <tag>     # or pin a specific release
```

Either form updates the plugin and regenerates the machine config.
An update usually just means new approved tool versions.

## Requesting a tool or version

1. Open a request per the internal OSS intake process
   (source review, trusted build, artifact upload to Nexus happen there).
2. Once the artifact is in Nexus, a catalog maintainer runs:

   ```bash
   scripts/add-version <tool> <version>
   scripts/validate-catalog
   scripts/verify-artifacts --checksum --tool <tool>
   ```

   For a brand-new tool, author `catalog/<tool>/tool.json` first
   (packaging description: artifact name template per platform, archive format, binary paths).
3. Open a merge request with the catalog diff.
   CI validates schemas, checks the artifacts exist in Nexus, and verifies checksums.
4. Once merged, the new version is live.
   Developers pick it up via `mise run vault-sync latest`.
   Tags are optional markers for pinning and rollback.

## Repository layout

```
metadata.lua       plugin identity
hooks/             mise backend hooks: list versions, install, exec env
lib/               shared Lua helpers
catalog/<tool>/    tool.json (packaging) + versions.json (approved versions + sha256)
config/            default Nexus base URL
schemas/           JSON Schemas for catalog files
scripts/           add-version, validate-catalog, verify-artifacts, vault-sync
install.sh         workstation bootstrap
tests/             fixtures for negative tests
experiment/        local Docker stack (Nexus + GitLab) and end-to-end test suites
docs/              design notes and research (see docs/research/SYNTHESIS.md for the decision log)
```
